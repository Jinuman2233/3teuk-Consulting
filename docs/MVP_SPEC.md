# 1. 문서 목적

이 문서는 3teuk-Consulting MVP의 제품 범위와
핵심 원칙을 정의한다.

개발자가 기능을 구현하기 전에
무엇을 만들고 무엇을 만들지 않을지 판단하는 기준으로 사용한다.


# 2. 해결하려는 사용자 문제

핵심 문제를 다음과 같이 정의한다.

해외에 거주하는 한국 학생과 학부모는
대한민국 대학 진학을 검토할 때

- 대학마다 서로 다른 입학처 사이트와 모집요강을 찾아야 한다.
- 학년도와 전형별 지원자격을 비교하기 어렵다.
- 재외국민, 해외고, 전교육과정 해외이수 등 관련 조건을 이해하기 어렵다.
- 여러 대학의 정보를 동일한 기준으로 비교하기 어렵다.
- 공식 규정과 개인 경험 또는 사교육 정보가 섞여 판단하기 어렵다.
- 오래된 정보와 최신 정보를 구분하기 어렵다.

이 플랫폼은 정보를 단순히 많이 모으는 것이 아니라
"공식 출처가 확인된 정보를 구조화하여 찾고, 비교하고,
자신의 상황과 연결해서 이해하기 쉽게 만드는 것"
을 목표로 한다.


# 3. 핵심 사용자

MVP의 주요 사용자는 다음 범위로 정의한다.

Primary users:

- 해외 국제학교에 재학 중인 한국 학생의 학부모
- 재외국민 특별전형을 검토하는 학생 및 학부모
- 12년 전교육과정 해외이수자 전형을 검토하는 학생 및 학부모
- 해외고 졸업 또는 졸업 예정자로 한국 대학 진학을 검토하는 학생과 학부모

Secondary users:

- 한국 복귀 후 한국 대학 진학을 검토하는 해외 체류 가정
- 대학별 해외고 지원 가능 전형을 조사하는 사용자

MVP에서 모든 유형의 국내 대학입시 사용자를 대상으로 하지 않는다.


# 4. 핵심 가치 제안

이 서비스의 핵심 가치는 다음 순서로 정의한다.

1. 정확성
2. 검증 가능성
3. 중립성
4. 최신성
5. 비교 가능성
6. 이해하기 쉬운 설명
7. 실제 경험 정보

정보량 자체를 가장 중요한 경쟁력으로 정의하지 않는다.


# 5. MVP 기능 범위

MVP 우선순위는 다음과 같다.

1. 대학전형 DB
2. 대학비교
3. 자격진단
4. 질문 FAQ
5. 학부모 경험 콘텐츠


## 5.1 대학전형 DB

목표:

사용자가 여러 대학 입학처와 PDF를 직접 찾아다니지 않고
대학별·학년도별·전형별 주요 정보를
일관된 구조로 확인할 수 있게 한다.

MVP에서 포함할 기능:

- 대학 목록
- 대학 검색
- 학년도 구분
- 전형 구분
- 대학별 전형 상세 페이지
- 지원자격
- 평가방법
- 제출서류
- 주요 일정
- 어학 관련 공식 규정
- 표준시험 관련 공식 규정
- 기타 주요 공식 조건
- 공식 출처
- 모집요강 또는 공식 문서명
- source page 또는 section
- 최종 확인일

중요:

공식 자료에서 확인되지 않은 항목은
추측해서 채우지 않는다.

자료 없음 / 확인 필요 / 공식자료 미확인 등의 상태를
표현할 수 있어야 한다.

MVP에서는 처음부터 모든 대한민국 대학을 수록하는 것을
목표로 하지 않는다.

초기 대상 대학 범위는 별도 데이터 구축 계획에서 결정한다.


## 5.2 대학비교

목표:

사용자가 서로 다른 대학 또는 전형을
동일한 기준으로 비교할 수 있게 한다.

MVP:

- 2~3개의 대학 또는 전형 선택
- 동일 academic_year의 전형만 하나의 비교표에서 비교
- 지원자격 비교
- 평가방법 비교
- 제출서류 비교
- 일정 비교
- 어학/표준시험 공식 규정 비교
- 각 항목의 공식 출처 확인

중요:

비교용 데이터를 별도로 복제하지 않는다.

대학전형 DB를 source of truth로 사용한다.

서로 다른 학년도 규정은
동일 조건 비교표에 섞지 않는다.

연도별 규정 변화 비교 기능은
향후 기능으로 남긴다.


## 5.3 자격진단

목표:

사용자가 자신의 해외교육 및 체류 이력을 입력하고
어떤 조건을 충족하거나 추가 확인해야 하는지
구조적으로 이해하게 한다.

MVP 원칙:

자격진단은 AI가 임의로 가능/불가능을 판단하는 기능이 아니다.

가능하면 공식 모집요강을 근거로 한
결정론적 rule 기반으로 설계한다.

자격진단은 다음 두 수준으로 구분한다.


### A. 기초 자격 점검

학생/부모/학교/재학/체류 이력을 분석한다.

university, academic_year, admission_type이
특정되지 않은 상태에서는
특정 대학 전형의 최종 "지원 가능" 판정을 하지 않는다.

기초 자격 점검에서 제공할 수 있는 결과:

- 조건별 상태
- 누락 정보
- 잠재적 미충족 조건
- 추가 확인사항

필요할 수 있는 입력 정보:

- 학생 국적
- 부모 국적
- 해외 재학 기간
- 학교 학제
- 이수 학기
- 출국 시점
- 입국/귀국 시점
- 졸업 예상 시점
- 부모 해외 체류 또는 근무 기간
- 중간 전학
- 월반
- 유급
- 기타 전형 판정에 필요한 조건


### B. 대학별 자격 확인

특정 대학의 자격 판단 시 반드시 다음을 특정한다.

- university
- academic_year
- admission_type

해당 조합의 공식 자료를 근거로 판단한다.

결과는 단순한

가능 / 불가능

만으로 제한하지 않는다.

예:

- 기본 조건 충족 가능성
- 특정 조건 미충족
- 추가 정보 필요
- 대학 공식 확인 필요

각 결과에는 가능하면

- 판정에 사용된 조건
- 근거가 된 공식 규칙
- 확인이 필요한 정보
- university
- academic_year
- admission_type
- 공식 출처

를 함께 제공할 수 있어야 한다.

자격진단 결과는 대학의 공식 지원자격 판정을 대신하지 않는다.


## 5.4 질문 FAQ

목표:

사용자가 반복적으로 궁금해하는 입시 규정과 용어를
공식 자료를 중심으로 쉽게 이해하도록 한다.

예상 카테고리:

- 재외국민 전형
- 3년 특례
- 전교육과정 해외이수
- 해외 학교 학제
- 학기 계산
- 부모 체류
- 제출서류
- 표준시험
- 대학별 절차

중요:

FAQ는

- official_fact
- 공식 자료를 바탕으로 한 설명

중심으로 구성한다.

전략적 의견, 개인 경험, 준비 노하우를
공식 규정과 섞지 않는다.

핵심 FAQ에는 가능하면 다음을 표시한다.

- academic_year
- official source
- source page/section
- verified_date

개인 경험과 노하우는
학부모 경험 콘텐츠 영역에서 다룬다.


## 5.5 학부모 경험 콘텐츠

목표:

공식 모집요강만으로 알기 어려운
실제 준비 과정과 경험을 공유한다.

예:

- 해외학교 생활
- 입시 준비 과정
- 서류 준비 경험
- 시험 준비 경험
- 대학 지원 과정
- 귀국 준비
- 시행착오
- 학부모 인터뷰

중요:

개인 경험은 공식 입시정보가 아니다.

모든 경험 콘텐츠는
"개인의 경험 또는 의견"임을 UI에서 명확하게 구분할 수 있어야 한다.

MVP에서는 자유게시판, 실시간 커뮤니티,
사용자 간 메시지 기능을 포함하지 않는다.


# 6. 정보 신뢰 구조

모든 핵심 입시정보는 가능하면 다음 정보를 함께 가진다.

- academic_year
- university
- admission_type
- source_url
- source_document
- source_page
- verified_date

사용자가 사이트에서

"이 정보가 어디에서 왔는지"
"몇 학년도 정보인지"
"언제 마지막으로 확인했는지"

확인할 수 있어야 한다.


# 7. 정보 유형 구분

향후 시스템에서는 가능하면 정보를 다음 유형으로 구분할 수 있도록 한다.

- official_fact
- interpretation
- strategic_opinion
- parent_experience
- unverified

official_fact와 parent_experience가
동일한 정보처럼 표현되지 않도록 한다.

FAQ는 official_fact와 공식 자료 기반 설명을 다루고,
strategic_opinion과 parent_experience는
공식 규정 FAQ와 섞지 않는다.


# 8. 핵심 사용자 흐름

MVP에서 최소한 다음 사용자 흐름을 지원하는 것을 목표로 한다.

Flow A:

홈
→ 대학전형 검색
→ 대학 선택
→ 학년도/전형 선택
→ 전형 상세 확인
→ 공식 출처 확인

Flow B:

대학전형 검색
→ 동일 academic_year의 2~3개 전형 선택
→ 대학비교
→ 차이 확인
→ 각각의 공식 출처 확인

Flow C:

자격진단
→ 학생/가족/학교 이력 입력
→ 기초 자격 점검
→ 조건별 상태 / 누락 정보 / 추가 확인사항 확인
→ 특정 university / academic_year / admission_type 선택
→ 대학별 자격 확인
→ 근거와 공식 출처 확인
→ 관련 대학전형 상세 페이지 이동

Flow D:

FAQ 검색
→ 공식 규정 설명 확인
→ academic_year 및 official source 확인
→ 관련 대학전형 또는 자격진단 이동

Flow E:

학부모 경험 콘텐츠
→ 경험글 확인
→ 해당 내용이 개인 경험임을 명확히 인지


# 9. MVP에서 제외하는 기능

현재 MVP에는 원칙적으로 다음 기능을 포함하지 않는다.

- 자유게시판
- 댓글
- 사용자 간 메시지
- SNS형 feed
- 학원 리뷰
- 입시 컨설턴트 리뷰
- 결제
- 구독
- 광고 시스템
- AI 챗봇
- 자동 대학 추천
- 합격 가능성 예측
- 합격선 예측
- 경쟁률 예측
- 모든 대학 자동 크롤링
- 모바일 앱
- 다국어 UI
- 복잡한 회원 등급
- 실시간 상담

향후 사용자 검증 후 별도 판단한다.


# 10. 개인정보 원칙

MVP에서는 가능한 한
학생 개인을 식별할 수 있는 개인정보를 저장하지 않는다.

자격진단을 위해 필요한 경우에도
최소한의 정보만 사용한다.

진단 결과 저장이나 회원 기능이 필요해질 경우
개인정보 설계를 별도 검토한 뒤 구현한다.


# 11. MVP 성공 여부 판단

근거 없는 숫자형 KPI를 임의로 만들지 않는다.

MVP 초기에는 다음 질문으로 제품 적합성을 검증한다.

- 사용자가 원하는 대학 정보를 실제로 더 빠르게 찾는가?
- 대학별 차이를 쉽게 이해하는가?
- 공식 출처 표시가 신뢰 형성에 도움이 되는가?
- 자격진단이 사용자의 혼란을 줄이는가?
- FAQ가 반복적인 질문을 해결하는가?
- 학부모 경험 콘텐츠가 공식정보와 다른 가치를 제공하는가?
- 사용자가 다시 방문할 이유가 있는가?

구체적인 KPI 목표치는 실제 사용자 테스트 후 설정한다.


# 12. 주요 위험

다음 위험을 제품 설계 단계부터 고려한다.

- 입시 규정의 연도별 변경
- 오래된 자료 노출
- 서로 다른 학년도 데이터 혼합
- 대학 공식자료 해석 오류
- 자격진단의 과도한 단순화
- 경험 콘텐츠를 공식정보로 오해하는 문제
- 데이터 업데이트 운영 비용
- 시장 규모가 예상보다 작을 가능성
- AI 검색 서비스가 대체재가 될 가능성


# 13. MVP 개발 원칙

개발 우선순위는 다음 사고 순서를 따른다.

사용자 문제
→ 필요한 정보
→ 데이터 구조
→ 정보 검증 방법
→ UX
→ 기능
→ 기술 구현

기능 수를 늘리는 것보다
핵심 데이터의 신뢰도와 사용성을 우선한다.


# 14. 향후 결정이 필요한 사항

현재 문서에서 임의로 확정하지 말고
별도 검토가 필요한 항목으로 남긴다.

- MVP에 포함할 대학 수
- 최초 대상 대학
- 대상 학년도
- 초기 전형 범위
- Supabase / database
- 관리자 입력 방식
- 콘텐츠 검수 workflow
- 회원가입
- 진단 결과 저장
- 서비스명
- 수익모델
