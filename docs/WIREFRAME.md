# WIREFRAME

이 문서는 3teuk-Consulting MVP 핵심 정보 흐름의
화면 구조를 정의한다.

실제 디자인 시안이 아니다.
다음 네 가지를 정의하는 UX 구조 문서다.

1. 정보의 우선순위
2. 화면 내 섹션 순서
3. 주요 사용자 행동과 CTA
4. 다른 페이지로 이동하는 흐름

색상, font, logo, 브랜드 디자인은 결정하지 않는다.

이 문서는 `AGENTS.md`, `docs/MVP_SPEC.md`, `docs/SITE_MAP.md`와
충돌하지 않도록 작성한다.

실제 대학의 가짜 입시정보를 만들지 않는다.
화면에 데이터가 필요하면

- [대학명]
- [전형명]
- [2027학년도]
- [확인일]
- [공식 문서명]

같은 placeholder만 사용한다.

아직 애플리케이션 코드, UI, database는 구현하지 않는다.


# 이번 Wireframe 범위

이번 문서에서 상세 설계하는 화면은 다음 4개다.

1. Home (`/`)
2. 대학전형 탐색 (`/universities`)
3. 대학 상세 (`/universities/[slug]`)
4. 전형 상세 (`/universities/[slug]/admissions/[academicYear]/[admissionSlug]`)

다음 화면은 아직 상세 wireframe을 만들지 않는다.

- 대학비교 (`/compare`)
- 자격진단 (`/eligibility`)
- FAQ (`/faq`, `/faq/[slug]`)
- 학부모 경험 (`/stories`, `/stories/[slug]`)

단, 핵심 4개 페이지에서 위 기능으로 이동하는 CTA는 표시한다.


# 1. 공통 Layout

Desktop 기준 기본 구조:

```
┌─────────────────────────────────────────────┐
│ [서비스명/로고]                             │
│ 대학전형 | 자격진단 | 대학비교 | FAQ | 경험 │
└─────────────────────────────────────────────┘

                         Page Content

┌─────────────────────────────────────────────┐
│ Footer                                      │
└─────────────────────────────────────────────┘
```

Global Navigation 순서:

1. 대학전형 → `/universities`
2. 자격진단 → `/eligibility`
3. 대학비교 → `/compare`
4. FAQ → `/faq`
5. 학부모 경험 → `/stories`

서비스명은 아직 결정되지 않았으므로
임의의 브랜드명을 만들지 않는다.

로그인/회원가입 버튼은 MVP에 표시하지 않는다.

# 3. 대학전형 탐색 Wireframe

Route:

`/universities`

목표:

사용자가
"특정 대학을 찾아가는 경우"
와
"조건을 기준으로 전형을 찾는 경우"
를 하나의 화면에서 모두 지원한다.


## 상단

```
------------------------------------------------
대학전형 찾기
------------------------------------------------

짧은 설명:

대학별·학년도별 전형 정보를
공식 출처 기준으로 탐색하는 화면.


Search:

[ 대학명 검색........................ ] [검색]
```


## 탐색 방식

다음 두 방식이 명확히 보이도록 한다.

```
[ 대학으로 찾기 ]     [ 조건으로 찾기 ]
```

이것이 tab인지 segmented control인지 등
구체적인 UI component는 아직 확정하지 않는다.

지원 가능 여부를 추정하는 필터는
자격진단과 혼동될 수 있으므로
현재 검색 필터에 넣지 않는다.


## A. 대학으로 찾기

대학교 목록 또는 검색 결과.

Card/List 기본 요소:

```
[대학명]

수록된 학년도:
[2027학년도] [2026학년도]

수록 전형:
[전형 유형 또는 전형 수]

최근 확인:
[확인일]

[ 대학 정보 보기 ] → /universities/[slug]
```

실제 대학명이나 가짜 수치를 사용하지 않는다.


## B. 조건으로 찾기

MVP 필터:

```
[학년도 ▼]

[전형유형 ▼]

[대학명 검색]
```

필터 적용 후 결과 영역:

```
검색 결과 [N]개
```

실제 숫자는 placeholder로만 표현한다.

결과 Card/List:

```
[대학명]

[academic_year]

[admission_type]

[전형명]

[정보 상태]

최종 확인:
[확인일]

[ 전형 상세 보기 ]
→ /universities/[slug]/admissions/[academicYear]/[admissionSlug]
```


## 정보 상태

Wireframe에서는 상태가 표시될 "위치"만 정의한다.

예:

```
[정보 상태]
```

실제 enum과 상태명은
DATA_MODEL 단계에서 결정한다.

"공식 확인", "업데이트 필요" 등의
최종 상태값을 이번 단계에서 확정하지 않는다.


## Empty State

검색 결과가 없을 경우:

"조건에 맞는 전형 정보를 찾지 못했습니다."

다음 행동이 가능하도록 한다.

- 검색 조건 변경
- 전체 대학 보기

가짜 전형을 추천하지 않는다.


# 4. 대학 상세 Wireframe

Route:

`/universities/[slug]`

목표:

한 대학에 수록되어 있는 입시정보를
학년도별로 탐색한다.


## 상단 정보

```
------------------------------------------------
[대학명]
------------------------------------------------

[공식 입학처 바로가기]

사이트 내 정보:

최종 확인:
[확인일]
```

공식 입학처 링크와
우리 사이트의 데이터 확인일은
서로 다른 의미임을 혼동하지 않도록 한다.


## 학년도 선택

```
학년도:

[ 2027학년도 ] [ 2026학년도 ]
```

기본적으로 하나의 academic_year만 활성화한다.

서로 다른 학년도 데이터를
같은 전형 목록에 혼합하지 않는다.


## 선택 학년도 안내

```
[2027학년도]

"현재 아래 정보는 선택된 학년도의 전형입니다."
```


## 전형 목록

각 전형 카드:

```
[admission_type]

[전형명]

정보 상태:
[상태]

최종 확인:
[확인일]


핵심 항목 Preview를 제공한다면
공식 데이터에 존재하는 정보만 표시한다.

예:

평가방법:
[데이터 존재 시 요약]
```

자료가 없으면 가짜 요약을 만들지 않는다.

CTA:

```
[ 전형 상세 보기 ]
→ /universities/[slug]/admissions/[academicYear]/[admissionSlug]
```


## 학년도 데이터가 없는 상태

해당 학년도 데이터가 없을 경우:

"현재 이 학년도의 전형 정보가 등록되어 있지 않습니다."

다른 연도 선택 CTA를 제공할 수 있다.


# 5. 전형 상세 Wireframe

Route:

`/universities/[slug]/admissions/[academicYear]/[admissionSlug]`

이 페이지를 MVP 핵심 정보 화면으로 취급한다.

비교용 데이터를 별도로 복제하지 않는다.
이 페이지가 읽는 대학전형 DB가 source of truth다.


## 5.1 상단 Identity 영역

```
------------------------------------------------
[대학명]

[2027학년도] · [admission_type]

[전형명]
------------------------------------------------

정보 상태:
[상태]

최종 확인:
[확인일]


[ 비교에 추가 ]           → /compare

[ 이 전형 자격 확인 ]     → /eligibility
```

"이 전형 자격 확인"은
`/eligibility`의 대학별 자격 확인으로 연결하며
다음 context를 전달할 수 있도록 설계한다.

- university
- academic_year
- admission_type


## 5.2 중요 안내

상단 또는 첫 정보 영역에서
다음 성격의 안내를 제공할 수 있도록 한다.

"본 정보는 해당 학년도의 공식 자료를 기준으로 정리되며
대학의 최종 지원자격 판정을 대신하지 않는다."

정확한 copy는 추후 확정한다.


## 5.3 Quick Navigation

정보가 길어질 가능성이 있으므로
다음 섹션으로 빠르게 이동할 수 있는 구조를 고려한다.

- 지원자격
- 평가방법
- 제출서류
- 일정
- 어학
- 표준시험
- 기타 조건
- 공식 출처

Sticky navigation 여부는
UI 설계 단계에서 결정한다.


## 5.4 지원자격

```
------------------------------------------------
지원자격
------------------------------------------------

[공식 확인 정보 표시 영역]
```

자료가 없을 경우 다음 상태를 지원할 수 있어야 한다.

- 공식자료 미확인
- 자료 없음
- 추가 확인 필요

이 섹션에는 가능하면
해당 내용의 근거를 확인할 수 있는
source reference 영역을 둔다.

```
근거:
[공식 문서명]
[p.xx 또는 section]
[출처 보기]
```

실제 문서나 페이지 번호를 임의 생성하지 않는다.


## 5.5 평가방법

동일 구조:

```
[평가방법 공식정보]

근거:
[source reference]
```


## 5.6 제출서류

문서 목록을 표현할 수 있는 구조.

각 항목이 다음 상태를 필요로 할 가능성이 있지만
실제 enum은 DATA_MODEL 단계에서 결정한다.

- 필수
- 조건부
- 확인 필요

근거 source를 연결할 수 있도록 한다.


## 5.7 원서 / 전형 일정

일정은 여러 event가 있을 수 있으므로
단일 text block으로만 설계하지 않는다.

예상 구조:

```
[일정명]       [기간/날짜]
[일정명]       [기간/날짜]
```

실제 일정은 입력하지 않는다.

각 일정에 필요한 경우
source reference를 연결할 수 있는 구조를 고려한다.


## 5.8 어학 관련 공식 규정

```
[official information]
```

자료가 공식 문서에서 확인되지 않는 경우
"요구하지 않는다"고 추론해서는 안 된다.

"공식자료에서 확인되지 않음"
등의 상태를 표현할 수 있도록 한다.

source reference 제공.


## 5.9 표준시험 관련 공식 규정

SAT / IB / AP 등의 기준을
공식 근거 없이 만들지 않는다.

데이터가 없다면
빈 상태 또는 미확인 상태를 사용한다.

source reference 제공.


## 5.10 기타 공식 조건 / 주의사항

전형 특수조건이나
사용자가 놓치기 쉬운 공식 조건이 들어갈 영역.

interpretation과 official_fact를
동일한 스타일로 보여주지 않도록 고려한다.


## 5.11 공식 출처

페이지 하단에
전형과 관련된 공식 source 전체 목록을 보여준다.

예상 구조:

```
------------------------------------------------
공식 출처
------------------------------------------------

[공식 문서명]

기관:
[대학/기관]

문서:
[source_document]

페이지/섹션:
[source_page / source_section]

확인일:
[확인일]

[ 공식자료 열기 ]
```

하나의 전형에 여러 공식 source가 연결될 수 있음을
Wireframe에 반영한다.


## 5.12 Source UX 원칙

전형 상세 페이지에서는
두 수준의 source 접근을 지원하는 구조를 설계한다.

A. Section-level source reference

지원자격, 제출서류, 일정 등에서
해당 정보의 근거를 바로 확인.

B. Full source list

페이지 하단에서
해당 전형과 연결된 전체 공식 자료 확인.

이것은 DB schema를 아직 확정하는 것이 아니라
향후 데이터 모델이 지원해야 할 UX 요구사항으로 기록한다.


## 5.13 하단 CTA

```
------------------------------------------------

[ 비교에 추가 ]           → /compare

[ 이 전형 자격 확인 ]     → /eligibility

------------------------------------------------
```

사용자가 긴 정보를 읽은 후에도
핵심 행동으로 이동할 수 있도록 한다.


# 6. 정보 유형 표현 원칙

Wireframe 단계에서 다음 정보 유형이
구분 가능한 구조여야 한다.

- official_fact
- interpretation
- unverified

학부모 경험은 핵심 4개 화면의
공식 입시정보 영역에 섞지 않는다.

향후 경험 콘텐츠로 연결할 경우에도
정보 성격을 분명히 구분한다.


# 7. Source와 Verified Date 원칙

전형 상세 상단의 verified_date:

전형 데이터 전체가
언제 마지막으로 검토되었는지 보여주는 위치로 설계한다.

동시에 핵심 정보 섹션에는
해당 내용의 출처 reference가 표시될 수 있어야 한다.

이번 단계에서는 다음을 결정하지 않는다.

- 전형 전체 verified_date를 DB에 하나 둘지
- section별 verified_date도 둘지
- source relation을 어떤 table로 구현할지

이것은 DATA_MODEL 단계에서 검토할 문제로 명시한다.


# 8. Mobile Wireframe 원칙

별도의 완전한 모바일 디자인은 만들지 않지만
각 화면의 mobile behavior를 기록한다.

Home:

기능 3개 카드를 세로 방향으로 배치 가능.

대학전형 탐색:

검색과 filter를 화면 너비에 맞게
세로 또는 접이식 구조로 제공 가능.

대학 상세:

학년도 선택을 작은 화면에서도
명확하게 사용할 수 있어야 한다.

전형 상세:

긴 본문을 한 열로 제공.

Quick navigation은
접이식 또는 horizontal scroll 등을 검토 가능.

CTA는 사용자가 쉽게 접근할 수 있어야 한다.

Desktop 비교표를
모바일에 단순 축소하는 방식은 피한다.

모바일 앱과 다국어 UI는 MVP 범위에 포함하지 않는다.


# 9. Loading / Empty / Error 상태

핵심 화면에서는 정상 상태만 설계하지 않는다.

Loading:

데이터를 불러오는 중임을 표현할 영역.

Empty:

다음 상태를 서로 구분한다.

- 검색 결과 없음
- 등록 전형 없음
- 공식 데이터 없음

Error:

데이터 로딩 실패 시
가짜 데이터로 대신 보여주지 않는다.

사용자에게 오류 상태와
재시도 가능성을 제공하도록 한다.


# 10. Accessibility 기본 원칙

향후 UI 구현 시 다음을 고려하도록 기록한다.

- 버튼과 링크의 역할 구분
- keyboard navigation
- semantic heading 구조
- 색상만으로 정보 상태를 전달하지 않음
- 적절한 contrast
- mobile touch target
- external official source 링크의 명확한 표시

→ 공식 출처 확인

전형 상세
→ 비교에 추가

전형 상세
